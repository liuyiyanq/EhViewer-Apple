# E-Hentai 下载限速与图片配额参考

用途：调整下载并发、重试、换节点之前先看这里。记录官方公开的规则、当前代码的实际节奏，以及两者对设计的约束
整理日期：2026-11-12（官方页面内容可能变化，改动前以原文为准）
相关文档：[EH-2 下载并发](下载并发不生效/TASK.md)、[EH-3 下载失败率高](下载失败率高/TASK.md)、[本期执行计划](PLAN.md)

## 主站与 H@H 的分工

| 角色 | 负责 | 和下载的关系 |
| --- | --- | --- |
| 主站（e-hentai.org / exhentai.org） | 网页、搜索、详情页、API（showpage）；给每页签发带签名、会过期的图片地址并指定 H@H 节点；管图片配额 | 每下一页都要先问主站要地址；限速和封 IP 都发生在这一侧 |
| H@H（Hentai@Home） | 志愿者运行的分布式图片节点，实际发图片 | 图片流量都在节点上；节点质量差异大，慢和超时多半来自差节点；不同页通常落在不同节点 |

- 换节点：带 `nl=<上次页面返回的 key>` 重新请求页面，主站换一个节点；没有可换的会给回原节点
- 原图：先请求主站 `/fullimg`，再 302 跳到节点

## 官方规则

| 主题 | 官方说法（要点） | 是否公开数值 | 来源 |
| --- | --- | --- | --- |
| 配额计数 | 每次 API 请求算 1 次，即使图片已缓存或请求失败也算；关闭 H@H 的用户每次算 5 次 | 是 | [Image Limits](https://ehwiki.org/wiki/Image_Limits) |
| 强制重载失败的图 | 算 50 次 | 是 | 同上 |
| 原图 | 按 10 × 文件大小（MB）计 | 是 | 同上 |
| 配额恢复 | 通常每分钟 3–5，随服务器负载变化 | 是（范围） | 同上 |
| 计数对象 | 默认按 IP；铜星捐赠、More Pages 特权或花 20,000 GP（24 小时，上限 10,000）可改为按账号 | 是 | 同上 |
| 配额用完 | 返回 509 提示图；"Could not get dispatch for image"，等几小时、用 GP 重置或买 More Pages | — | [Technical Issues](https://ehwiki.org/wiki/Technical_Issues) |
| 打开页面太快 | 提示 "opening pages too fast"，不退让会自动封 IP；短时间大量请求会被当作自动抓取软件临时封禁 | 否 | 同上 |
| 连接数过多 | 短时间开大量连接会被自动阻断，表现为页面加载中连接被取消 | 否 | 同上 |
| H@H 节点按 IP 限流 | 客户端自带按 IP 的连接频率限制（`--disable-flood-control` 可关） | 否 | [Hentai@Home](https://ehwiki.org/wiki/Hentai@Home) |
| H@H 节点最大连接数 | 20 + 峰值速度/10000，上限 500 | 是 | 同上 |
| 只用 443 端口节点 | 网站设置可选 "Default port clients only"，只走 443 端口的节点 | — | [Image Limits](https://ehwiki.org/wiki/Image_Limits)、[Technical Issues](https://ehwiki.org/wiki/Technical_Issues) |
| 绕开 H@H | 捐赠者可用 `?nl=1` 或设置里的 "No" 选项直连，会很快耗尽配额 | — | [Technical Issues](https://ehwiki.org/wiki/Technical_Issues) |

第三方参考（非官方）：

- gallery-dl 对 exhentai 默认每个请求间隔 3–6 秒（[gallery-dl.conf 手册](https://manpages.ubuntu.com/manpages/plucky/man5/gallery-dl.conf.5.html)）
- 逐张下载消耗图片配额，归档下载消耗 GP（[JHenTai Wiki](https://github.com/jiangtian616/JHenTai/wiki/Common-Questions)、[gallery-dl 讨论](https://github.com/mikf/gallery-dl/discussions/5699)）

## 当前代码的下载节奏（v1.3.2，工作区，含 EH-10）

| 项 | 现状 | 位置 |
| --- | --- | --- |
| 画廊并发 | 一次只下一本，整本结束才开始下一本 | `DownloadManager.processQueue`（单个 `activeTask`） |
| 单本页并发 | 「下载线程数」，默认 3，设置页可调 1–7（存储层夹在 1–10） | `SpiderQueen.maxConcurrent`、`AppSettings.multiThreadDownload`、`SettingsView` |
| 全局图片并发 | 最多 10，实际跟随线程数 | `EhRateLimiter.maxImageConcurrent` |
| 下载时的主站请求 | 详情页、showpage、页面 HTML 均不限速 | `EhRateLimiter.waitApiSlot(priority: .download)` 直接放行 |
| 浏览时的主站请求 | 每秒 2 次，突发 3 | `EhRateLimiter` 令牌桶 |
| 单页重试 | 最多 5 次，重试间不等待；图片下载失败先同地址重试 1 次，再不带 `nl=` 重新向主站要 1 次地址，仍失败判本页失败；下载不再用 `nl=` 换节点 | `SpiderQueen.loadPage`、`maxPageAttempts` |
| 图片超时 | 连接与两次收到数据的间隔固定 10 秒；单张总时长不限（已去掉设置） | `EhAPI.fetchDownloadImage`、`downloadImageIdleTimeout` |
| 下载延迟 | 下载模式下每页从网络下完后等待，默认 0 | `SpiderQueen.waitDownloadDelay` |
| 509 | 识别到 509 提示图或状态码 509 后，停止本本剩余页，整本判失败 | `SpiderQueen.handleImageLimitReached` |

## 对设计的约束

1. 配额才是大量下载的真正上限。配额在问主站要地址时扣，恢复很慢；下得越快只会越早遇到 509，提速主要是减少空等，而不是多拿图
2. 换节点代价高。如果 `nl=` 就是官方说的"强制重载"，每换一次扣 50 次（EH-10 之前"失败即换、最多 3 个"一页最多多扣约 150 次，安卓"每次失败都换"最多约 200 次）。11-16 起下载不再用 `nl=`：先对同一个地址重试（不经过主站，不扣配额），仍失败不带 `nl=` 重新要一次地址（扣 1 次），与 fork 前一致；不做"同一页同时向两个节点下载"
3. 对节点可以放开并发，但要分散：总并发 8–10，同一节点 2–3 个连接，避免触发节点的按 IP 限流
4. 对主站要保守：下载时的地址请求也应限速，并且只少量预取（地址会过期）
5. 网络环境封非标准端口（如办公网）时，打开 "Default port clients only" 可能比任何重试策略都有效；App 已同步图片分辨率等网站设置，可以照着加
   - 11-16 用户实测：办公网下不换节点时总有几页下不完，在网站设置里改为 Default port clients only 后可以下完
