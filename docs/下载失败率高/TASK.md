# EH-3 下载失败率高，同一画廊需反复下载才能补齐

目标：网络正常时，一次下载就能拿到整本画廊；单页失败能在本轮内自动恢复；暂停或恢复后画廊状态正确
范围与不做项：涉及 SpiderQueen 页面加载与重试、取消，DownloadManager 收尾判定，后台下载；不加失败日志（端侧尽量修复，剩余失败靠用户手动重试兜底）；不改阅读器的网络路径，不改 E-H 账号配置
事项类型与 TAPD 关键字：无 TAPD，本地编号 EH-3
相关文档：[EH-2 下载并发](../下载并发不生效/TASK.md)；执行顺序与跨任务约束见 [本期执行计划](../PLAN.md)

## 行为与契约

允许变化：单页重试策略（换节点、退避时长）；SpiderQueen 改为复用 EhAPI 的回退和限速；取消与收尾判定
必须保持：全局图片请求并发上限 5；页面与接口请求全局不超过每秒 2 次；下载时浏览、阅读的请求优先；已下载的页不重复下载；暂停后不再产生新请求；509 时停止继续请求并通知用户；`.ehviewer` 文件格式不变

| 输入或事件 | 预期结果 | 依据 |
| --- | --- | --- |
| 某页图片所在的 H@H 节点不可用 | 用 `nl=` 换节点后成功，不计入失败 | 原因 1 |
| 主域名 DNS 污染或 TLS 被拦 | 走域名前置回退，与阅读器行为一致 | 原因 2 |
| 下载中暂停 | 所有在途页面任务停止，不再有请求 | 原因 3 |
| 暂停后立即恢复 | 只有一个 SpiderQueen 在跑，最终状态由这一轮的结果决定 | 原因 3 |
| 下载进行中打开画廊详情或翻页 | 浏览的请求排在下载请求之前，等待不超过约 0.5 秒 | 修复方式第 3 项 |
| 暂停时有页面请求在排队等限流 | 排队的请求直接取消，不再发出 | 修复方式第 1、3 项 |
| E-H 返回"页面打开太快"提示页 | 识别为限流，下载请求整体暂停一段时间后再继续，不把该页判为失败 | 修复方式第 3 项 |
| 图片配额用完（509） | 停止派发剩余页，状态为失败并提示 509，不把剩余页逐一判为失败 | 网络侧 |

原因定位（调研结论，未经真机验证）：

- 1 失败后不换 H@H 节点：`skipHathKey` 已解析出来，但没被使用（`Packages/EhSpider/Sources/EhSpider/SpiderQueen.swift:502-507`）。5 次重试的退避总共只有约 7.5 秒（同文件 :297-300），重试大概率还是同一个坏节点。阅读器有换节点逻辑（`ehviewer apple/ReaderViewModel.swift:848`），下载器没有
- 2 下载器绕开了 EhAPI：直接用裸 `URLSession`（`SpiderQueen.swift:40-61`），所以没有域名前置回退、没有 Cookie 清洁，页面和接口请求也不受每秒 2 次的限速，并发时容易触发 E-H 的"页面打开太快"（返回 200 和提示页，被当成解析失败）。另外图片请求超时写死 30 秒（:319），设置页的超时对它不生效
- 3 取消无效导致竞态：`cancelAll` 只取消 `activeTasks`（:185），而下载模式的页面任务在 TaskGroup 里（:144），从未登记进去，所以暂停、删除、后台过期都停不掉旧下载。恢复后同一个 gid 会有新旧两轮同时跑；旧一轮收尾时 `runningGid == gid` 的检查会通过（`Packages/EhDownload/Sources/EhDownload/DownloadManager.swift:468`），于是用旧结果把画廊标成失败、清掉新 spider 的引用，并提前启动队列里的下一本
- 4 后台：`beginBackgroundTask` 只有约 30 秒，过期后在途请求恢复时会集中报错，把重试用光；BGProcessingTask 启动下载 2 秒后就报告完成（`ehviewer apple/BackgroundDownloadManager.swift:113-116`）；回到前台不会自动恢复下载
- 5 条件性：pToken 按每个详情页 20 张缩略图计算（`SpiderQueen.swift:389`），`SpiderInfo.previewPerPage` 从未赋值。如果账号设置的每页缩略图数不是 20，会有一段固定的页永远拿不到 pToken。用户反馈"反复下载能补齐"，与此不符，大概率不是当前主因
- 6 可观测性：页面失败只 `print` 输出（`DownloadManager.swift:747`），没有进入 LogManager。用户决定不处理
- 7 限流器本身不严格（2026-11-11 补充）：`waitApiSlot`（`Packages/EhCore/Sources/EhSettings/EhRateLimiter.swift:42`）发现没有 token 时各自睡一段时间，醒来后不管有没有 token 都放行（`max(0, apiTokens - 1)`）。多个请求同时等待时会一起放行，并发下实际速率会超过每秒 2 次；等待者之间也没有先后顺序和优先级
- 8 没有识别"页面打开太快"：代码中没有任何地方识别 E-H 的这个提示页

修复方式（计划，按优先级）：

1. 取消与收尾：在 SpiderQueen 中保存 `startDownload` 所在的 Task 句柄，`cancelAll` 时一并取消；DownloadManager 的 `runningGid` 改为每轮唯一的运行编号，旧一轮收尾时因编号不匹配直接退出
2. 换节点重试：图片下载失败时用 `skipHathKey` 带 `nl=` 重新取页面，同一页最多换 3 个节点，规则与阅读器一致；退避基数按 `downloadDelay` 设置，并延长总的重试窗口
3. 网络层：页面请求和接口请求改走 EhAPI（获得回退、Cookie 清洁和限速），图片请求复用 EhAPI 的域名前置回退；图片请求超时改读设置值。同时改限流器：
   - 改为排队放行：等待者进入队列，每产生一个 token 只放行一个，保证全局不超过每秒 2 次
   - 分两个优先级：浏览、阅读为高优先级，下载为低优先级；有高优先级请求排队时先放行它
   - 排队可取消：任务取消时从队列移除，不再发出请求（配合第 1 项）
   - 识别"页面打开太快"提示页：低优先级队列整体冷却一段时间（初定 10 秒）
   - 不另建线程池：单本画廊的并发页数已由 TaskGroup 和「并发线程」设置限制，速率由限流器控制
4. 509：检测到后停止派发剩余页，并通知 DownloadManager 把整本置为失败
5. 后台：BGProcessingTask 等当前一本完成或过期再报告完成；回到前台时调用 `kickQueue` 恢复处于等待状态的任务
6. previewPerPage：从详情页解析每页缩略图数，写入 SpiderInfo 并用于计算 pToken 所在页（低优先级）
